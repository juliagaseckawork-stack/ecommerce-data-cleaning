# Data Auditing: internal_inventory_raw and supplier_feed_raw

I wrote these queries to audit the source tables on the BigQuery project `ecommerce-analysis-503909` before starting the data cleaning phase. The objective of this script is solely to classify problems, not to resolve them. Every check I wrote is limited to observing the data and never modifies it.

## Context and Query Order

I worked on two tables: `internal_inventory_raw` and `supplier_feed_raw`. The internal table is our master source because it contains the descriptive identity of the product (name, category, price, etc.). The supplier table is leaner and limited to stock and costs.

The queries were executed in a precise order: first the complete audit of internal, then that of supplier. This is not an aesthetic choice, but a logical dependency.

For internal, I structured the checks sequentially. First, I verified string integrity (spaces, NULLs, placeholders), because an extra space or an "N/A" would cause subsequent checks to fail or be bypassed. Then I checked format, uniqueness, and casing, which depend on already cleaned strings. Finally, I validated numerical values, which makes no sense to check if the primary key is corrupted.

For supplier, I first performed a single-source audit, which is much more compressed since the table has fewer columns. Only at the end did I perform the cross-system integrity check. Joining two dirty tables would only mask the origin of errors, and it only makes sense to classify a SKU in the supplier as an "orphan" after verifying that the master table (internal) is intact.

## SQL Patterns Used

For multiple flagging, I used `ARRAY_TO_STRING` combined with `IF` statements. Initially, I thought about creating one query per check, but scanning the table six times in BigQuery costs too much in terms of processing. I also tried nested `CASE WHEN` statements, but the problem was that they returned only the first error found per row. With the array, if a row has both a trailing space and a placeholder, I see both. `ARRAY_TO_STRING` skips the `NULL`s generated by the `IF`s when there are no errors, so the separator appears only between actual flags.

For window functions, I leveraged `QUALIFY`, which is specific to BigQuery. It avoids writing a subquery just to filter results and saves me from having to list all columns to exclude the ranking column.

I used `UPPER(TRIM())` wherever matching or grouping was required, but kept it strictly separate from format checks. If I had normalized during format checks as well, I would never have caught SKUs written with incorrect casing.

To check if stock and reorder points are integers, I used `FLOOR(x) != x` instead of `CAST`. A `CAST` on a non-integer float in BigQuery fails, or silently truncates if I use `SAFE_CAST`. I only need a boolean predicate for the check, I don't want to transform the data. Same logic applies to price decimals: I use `ABS(retail_price - ROUND(retail_price, 2)) > 0.00001`. I can't do a simple `!=` because floating-point numbers in memory can have machine precision issues (like `19.989999999999998`), and the threshold saves me from false positives.

To find extreme prices per category, I used `ARRAY_AGG(... ORDER BY ... LIMIT 1)[OFFSET(0)]` instead of `ROW_NUMBER`. It avoids additional CTEs and, by adding the product name in the ORDER BY, makes the result deterministic even in case of ties.

The technically most complex choice was cross-source integrity. Instead of a `FULL OUTER JOIN`, I united the tables with `UNION ALL` and counted occurrences with `COUNTIF`. If I had used a join, I would have had to normalize SKUs twice in the condition. More importantly, with the 3 internal duplicates, the join would have generated a cartesian product, hiding the duplicate. With counts, however, I immediately see if there are more rows on one side or the other.

Finally, I always put `WHERE sku IS NOT NULL AND TRIM(sku) != ''` at the beginning of aggregation queries. It seems redundant since I count NULLs in a dedicated check, but I need it to prevent null or empty keys from ending up in the `GROUP BY` creating phantom groups.

## Specific Choices on Individual Checks

For SKU format, I use two cascading regexes. The first is case-insensitive and checks only the structure. If it passes, the second checks the exact casing. So if I find `sku-1015`, I classify it as a casing error and not a structural format error. I also put a `TRIM` inside the regex to avoid overlapping with the space check.

For "dirty NULLs" (like 'N/A', 'null', '-'), I use `LOWER(TRIM(x)) IN (...)`. It is much more readable and easier to extend than writing a giant regex with alternations.

For suspicious symbols in product names, I use a whitelist regex. I define allowed characters rather than prohibiting those I imagine are illegitimate, because blacklists are always incomplete. I use raw strings with double quotes to avoid struggling with apostrophe escaping.

I checked for duplicates on `UPPER(TRIM(product_name))` as well. I caught 8 products with different SKUs but the same name. If I had looked only at the key, I would never have seen them. For categories, instead of searching for specific values, I did a `GROUP BY LOWER(TRIM(category))` and counted distinct variants. If for "sports" I find two different spellings, I have an inconsistency.

For names that are too short or long, I used two `ROW_NUMBER`s in the same CTE to do some exploration on boundary values. The check `!= 15` on the reorder point is instead a specific business constraint for this project.

## The Results

Here is what I found across the tables:

On `internal_inventory_raw`:
*   8 rows with spaces (trailing, leading, or internal) on SKUs.
*   10 total NULLs (5 on category, 5 on reorder_point).
*   Zero placeholders or "dirty nulls".
*   Zero format or casing errors on SKUs, and zero strange symbols in product names.
*   3 duplicate SKUs (SKU-1015, SKU-1108, SKU-1301) with conflicting prices or categories.
*   11 duplicate product names (22 total rows), of which 8 have different SKUs.
*   Zero anomalies on category casings and name lengths.
*   8 numerical anomalies on retail prices (4 negative, 4 zero). Zero errors on decimals.

On `supplier_feed_raw`:
*   Zero key integrity errors and zero duplicates.
*   10 casing mismatches on SKUs, zero structural errors.
*   Numerical values (cost and stock) all valid and integers.

In the cross-system check, I found 8 match issues: 3 are the known internal duplicates, 5 are SKUs present only in the supplier (the orphans, from SKU-9991 to SKU-9995).

The last query in the supplier file is the only hardcoded one (`WHERE UPPER(TRIM(sku)) LIKE 'SKU-999%'`). I wrote it this way because it is the operational complement of the cross-system check: the general check finds orphan SKUs, this one inspects them in detail with their stock and cost values. I preferred to separate the general audit query, which must remain reusable, from this punctual investigation.
